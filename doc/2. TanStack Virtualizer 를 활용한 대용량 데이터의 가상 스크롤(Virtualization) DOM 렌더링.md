

# [ TanStack Virtualizer로 구현하는 대용량 데이터 가상 스크롤 ]

> DOM 렌더링 구조와 Virtualization 동작 원리

---

**`DownEventPage` 화면에서 렌더링되는 카드 개수**는 **데이터 페이징 단위**와 **가상 스크롤(Virtualization) DOM 렌더링** 2단계로 나누어 동작합니다.

---

## 1. 데이터 페이징 기준 (메모리 로드)
* **페이지 당 데이터 수 (`pageSize`)**: 기본 **`10개`** (페이지네이션에서 10, 20, 50, 100 선택 가능)
* 백엔드 API로부터 한 페이지에 해당하는 `pageSize`개(기본 10개)의 다운 이벤트 카드 목록을 가져옵니다.

---

## 2. 실제 화면(DOM) 렌더링 기준
전체 10개(또는 100개)가 브라우저 DOM에 한 번에 모두 렌더링되지 않고, **`TanStack Virtualizer`(`useVirtualizer`)를 통한 가상 스크롤**이 적용되어 있습니다.

```typescript
// 1. 초기 추정치 estimateSize : 일반적인 모니터(1920×1080 해상도) 기준 480px로 가상 배치
// src/pages/down-event/ui/down-Event-page.container.tsx
const rowVirtualizer = useVirtualizer({
  count: events.length,
  getScrollElement: () => scrollContainerRef.current,
  estimateSize: () => 480, // 카드 예상 높이 (px)  👈  필요시 조정 필요!
  overscan: 2, // 상/하단 버퍼 2개
});

...[ 중간 생략 ]...

// 2. 실제 마운트 시 브라우저가 DOM 높이를 '실측'하여 즉시 덮어씀
<div
  key={event.downEventId}
  data-index={virtualRow.index}
  ref={rowVirtualizer.measureElement} // 👈 사용자 모니터 환경의 실제 픽셀 높이 자동 감지
  style={{ transform: `translateY(${virtualRow.start}px)` }}
>
  <DownEventCard ... />
</div>
```

---

## 3. 화면에 실제 렌더링되는 DOM 요소 개수
* **`virtualRow.index`**: 가상 스크롤에 사용되는 데이터 배열(`events`)의 **인덱스**
* **실제 DOM 요소 개수**: `events.length` 전체가 아니라 **`virtualItems.length`** 만큼만 렌더링

예시:

```typescript
// src/pages/down-event/ui/down-Event-page.container.tsx
const virtualItems = rowVirtualizer.getVirtualItems();

// 렌더링되는 요소 개수 = virtualItems.length (기본 3~6개)
{virtualItems.map((virtualRow) => (
  <div
    key={events[virtualRow.index].downEventId}
    data-index={virtualRow.index}  // 👈 인덱스는 0~499이지만 실제 렌더링은 3~6개만!
    ref={rowVirtualizer.measureElement}
    style={{ transform: `translateY(${virtualRow.start}px)` }}
  >
    <DownEventCard ... />
  </div>
))}
```
## 4. 상/하단 버퍼 2개
* **`overscan: 2`**로 설정된 이유는 크게 **`2가지 목적(빈 화면 깜빡임 방지 + 카드 상세 데이터 사전 로딩)`**이 결합되어 있기 때문입니다.


### 1). 스크롤 시 빈 화면(White-out) 및 깜빡임 방지

* **`overscan: 0`인 경우**:
  * 화면에 정확히 보이는 카드만 DOM에 렌더링합니다.
  * 사용자가 휠을 빠르게 굴릴 때, 브라우저가 새 카드의 DOM을 생성하고 그리는 동안 **순간적으로 빈 흰색 여백(White-out)**이 노출되어 버벅거리는 느낌을 줍니다.
* **`overscan: 2`인 경우**:
  * 현재 화면 위/아래 보이지 않는 영역에 **각각 2장씩 카드를 미리 DOM에 렌더링(버퍼)**해 둡니다.
  * 빠른 스크롤이 발생해도 이미 렌더링된 버퍼 영역이 먼저 보이므로 끊김 없이 부드러운 스크롤을 유지합니다.

### 2). 카드 단건 상세 데이터 및 이미지의 "병렬 프리패치(Prefetch)" 연동

* 이 프로젝트의 [**`DownEventCard`**]는 카드가 DOM에 마운트되는 순간 단건 상세 API(`useActionPopupQuery`)를 호출하여 조치 내용(HTML), 첨부 이미지 등을 가져옵니다.

```tsx
// DownEventCard 컴포넌트 내부
const { data: actionDetail } = useActionPopupQuery(data.downEventId);
```

* 상하 2건이 미리 마운트되어 있으면, **사용자가 스크롤을 내려 해당 카드를 마주하기 직전에 백그라운드에서 상세 데이터 및 이미지를 미리 호출(Prefetch & Cache)**해 둡니다.
* 그 결과, 사용자가 스크롤을 내렸을 때 로딩 스피너(`Loader2`)를 기다리지 않고 **이미 완성된 카드 내용을 즉시 확인**할 수 있습니다.

---

### 3). 왜 하필 `2건`인가? (비용과 UX의 최적 균형점)

| `overscan` 개수 | 장점 | 단점 |
| :--- | :--- | :--- |
| **0 ~ 1건** | 메모리 소모 극소화 | 빠른 스크롤 시 빈 화면 노출 및 이미지/데이터 로딩 지연 발생 |
| **2건 (선택)** | **부드러운 스크롤 보장 + 적절한 사전 로딩(프리패치)** | 총 마운트 카드 수 **약 5~6개**로 브라우저 메모리 부하 거의 없음 |
| **4건 이상** | 사전 로딩 범위 넓음 | 렌더링 카드 수가 10개 이상으로 늘어나 **가상 스크롤의 성능/메모리 절감 효과가 퇴색**됨 |

따라서 **대용량 이미지/HTML 렌더링 성능을 지키면서도 스크롤 지연을 없애는 최적의 균형 수치가 `2건`**입니다.

---

## 5. 결론 요약

`TanStack Virtualizer`가 적용된 이 화면에서 실제로 브라우저 DOM에 올라와 **`렌더링되는 다운 이벤트 카드의 개수(DOM Nodes)`**는 다음과 같이 동작합니다.

* **실제 DOM에 마운트되는 카드 수**: **약 `3 ~ 6개`**
  - **화면 가시 영역 (Viewport)**: 모니터 높이에 따라 약 **`1 ~ 3개`** 노출
  - **오버스캔 버퍼 (`overscan: 2`)**: 스크롤 대비 상/하단 **`2 ~ 4개`**
* 스크롤을 내릴 때 화면 밖으로 벗어난 카드는 DOM에서 즉시 언마운트(제거)되고, 화면에 진입하는 카드만 동적으로 렌더링되어 대용량 이미지/HTML 렌더링 시에도 메모리와 성능을 최적 상태로 유지합니다.
